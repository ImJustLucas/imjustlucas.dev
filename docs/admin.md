# Admin

Read before touching `app/admin/`, `lib/admin/`, the Admin's sign-in or its environment variables.

## Access and sign-in

`app/admin/` is the Owner's private space: French, server-rendered, `noindex`, out of the menu and outside Locale routing (so no `proxy` logic; the access check lives in the Admin itself). `app/admin/layout.tsx` is the Admin's own root layout and its gate: anyone but the signed-in Owner gets the sign-in or refusal screen. Sign-in is GitHub OAuth (scope `public_repo`, the token later used to commit content): `app/admin/auth/sign-in` redirects to GitHub, `app/admin/auth/callback` keeps the identity in an iron-session sealed cookie for 12 hours (no database; the token is kept for the Owner only); any failure there (forged state, declined consent, GitHub refusing the code or unreachable, missing configuration) signs nobody in and redirects back to the sign-in screen, logging no GitHub error text. Signing out (`signOut` in `lib/admin/github-sign-in.ts`) revokes the Owner's token through `DELETE /applications/{client_id}/token` (best effort) and always ends the session. The OAuth App's `public_repo` token can write to every public repository of the Owner; a GitHub App installed on this repository only would narrow that reach (not done). The one Owner check is `ownerAccess` in `lib/admin/owner-access.ts`, behind the `AdminIdentitySource` interface. The Admin layout and home page read it through `currentOwnerAccess()` (`lib/admin/session.ts`); editor pages and every content Server Action reach it through `AdminAccess` (below), which refuses anyone but the Owner with `not-owner`, so each action checks the Owner itself, as Server Actions are public endpoints. Tests use a fake identity source (`owner-access.test.ts`) and a fake GitHub (`github-sign-in.test.ts`).

## Editing content

Content editing follows one pattern, to copy for every editor. `lib/admin/admin-action.ts` holds `AdminAccess` (the signed-in Owner's content repository, or `NotOwner`) and `saveContent(revision, edit)`: read the content through the catalog's `loadContent` at the revision the editor was opened at (never the branch's possibly lagging current state), apply the edit, validate the whole result with the `Content` schema (issues inside the edited entry, an indexed entry or a whole document like the Profile, become French field errors keyed by input path, e.g. `name.fr`, `techs.1`, `links.github`; any other issue refuses the save), then commit only the changed documents, with any files the edit uploads (`assets`), as one commit on top of the revision the editor was opened at, on the content branch (`main` unless `CONTENT_BRANCH` says otherwise). An upload travels in the editor's form, picked with `FileField` (`app/admin/file-field.tsx`), and reaches the action as an `Upload` (a lazy read) that `saveContent` reads only after the Owner check. Which files are accepted is `lib/admin/upload.ts` (plain code, also read by `FileField`): each kind's formats recognised from the file's bytes (an image: PNG, JPEG, WebP or AVIF; a PDF), one 4 MB limit and one set of French messages. A Project image or an Achievement's art (`lib/admin/uploaded-image.ts`, stored as `public/images/projects/<title>-<fingerprint>.<ext>` or `public/images/achievements/<English name>-<fingerprint>.<ext>` so a new image never reuses a cached URL; `imageUpload` in `admin-action.ts` reads it and returns the path, the asset to commit or a field error) is committed with its entry; a Resume is committed over its Locale's current file, with the Profile dating that Resume to the upload day in Europe/Paris (read with Effect `Clock`); `experimental.serverActions.bodySizeLimit` in `next.config.ts` (4.5 MB, Vercel's cap; Next cannot scope it to one action) lets it through. Every action returns an `AdminActionResult` (`lib/admin/action-result.ts`, plain data): `saved`, `invalid`, `refused`, `conflict`, `not-owner` or `failed`. Actions per kind live in `lib/admin/<kind>.ts` (e.g. `techs.ts`: Techs, whose identifier is fixed once created, and which cannot be deleted while a Project uses them; `experiences.ts`: Experiences, addressed by their position in the stored document; `projects.ts`: Projects, likewise, with their Rarity and their optional place on the home page (empty: not featured); both editors list them in Period order like the public pages, each with its stored position, through `inPeriodOrder` in `admin-action.ts`, while Techs are listed in stored order; `achievements.ts`: Achievements, addressed by stored position and listed in stored order, their public order, each with its art, uploaded or kept; `hobbies.ts`: Hobbies, likewise, which the Owner also moves up and down (`moveHobby`; the first moved up or the last moved down commits nothing); `profile.ts`: the Profile's links and account identifiers, and Resume uploads), with an `open…Editor`; what they share is in `admin-action.ts`: `openEditor(view)` (reads the revision, then the content at exactly that revision, gives anyone but the Owner `not-owner`, and gives the Owner `unavailable` with a French reason when the content can't be read, e.g. a branch without it, which the page shows with `ContentUnavailableScreen`), the `Saved` input (that revision), `commitMessage` (`📝 Admin: …`), `documents` and the `gone` refusal for an entry that no longer exists; they are tested in `lib/admin/<kind>.test.ts` against an in-memory repository and a fake identity. `lib/admin/server.ts` (server only) is the only place that runs them, over the session and the GitHub repository (`contentRepository()` in `lib/admin/config.ts`): pages call its `get…Editor()` functions, Server Actions its one generic runner `runAdminAction(action, input)`, and both get plain data back, so no React component imports Effect. Each editor page (`app/admin/<kind>/page.tsx`) has a `"use server"` `actions.ts` that reads its form with the helpers of `app/admin/action-form.ts` (`field`, `localized`, `index`, `techIds`, `upload`) and calls `publish(action, input)`, which runs the action and calls `refresh()` after a save; its forms use `AdminForm`, `AdminField`, `LocalizedField` and `SelectField` (a fixed choice, e.g. a contract type, a Hobby's pose, or a Rarity through `RarityField` in `app/admin/rarity-field.tsx`) from `app/admin/admin-form.tsx`, and a Period is entered with `PeriodField` (`app/admin/period-field.tsx`: year and optional month for start and end, "en cours" as an end) and read back in the action with `readPeriod` (`app/admin/period-input.ts`, tested in `period-input.test.ts`) as a `PeriodInput` (`lib/admin/action-result.ts`, the one type of a Period as typed); the "live in about a minute" notice comes from `AdminNoticeProvider` in the Admin layout.

## Environment variables

Admin environment variables (`.env.local` locally, Vercel Production); `scripts/wizards/admin-github-oauth.sh` creates the OAuth apps and sets them all:

| Variable | Value |
| --- | --- |
| `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | GitHub OAuth app credentials; one app per environment, callback `<origin>/admin/auth/callback` |
| `SESSION_SECRET` | ≥ 32 characters, encrypts the session cookie; changing it signs everyone out |
| `OWNER_GITHUB_ID` | The Owner's numeric GitHub id (`gh api user -q .id`); unset means nobody gets in |
| `AUTH_REDIRECT_URI` | Optional, pins the callback URL (set on Production); otherwise derived from the request |
| `CONTENT_BRANCH` | Optional, the branch the Admin reads and commits content to (default `main`); e.g. a pull request's branch in `.env.local` to try the Admin before merging it |
