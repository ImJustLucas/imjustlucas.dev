# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
pnpm dev        # Start dev server (Turbopack is the default bundler)
pnpm build      # Production build
pnpm lint       # ESLint CLI with flat config in eslint.config.mjs (runs in CI on every push)
pnpm test       # Vitest, runs every *.test.ts once (runs in CI on every push)
```

Tests use Vitest (`vitest.config.ts`, Node environment, `@/` alias resolved from `tsconfig.json`, `server-only` aliased to a no-op). They sit next to the module they cover as `*.test.ts` and exercise plain functions, or Effect services through `@effect/vitest` (`it.effect`), through their public interface; React components are not tested. The pre-commit hook exists but its commands are commented out.

## Architecture

Personal portfolio site built with Next.js 16 (App Router, Turbopack), React 19, Tailwind CSS, and Shadcn/ui.

**Routing** — every public page lives under `app/[locale]/` (Locales `en`, default, and `fr`, defined in `i18n/routing.ts`) and is statically generated for both. `app/[locale]/layout.tsx` is a root layout (there is no `app/layout.tsx`, as `next/root-params` needs the Locale segment to be the root), so the Admin path can add its own root layout beside it; shared fonts are in `app/fonts/index.ts`. `proxy.ts` (next-intl middleware) sends the root address to the Locale of the browser language, falling back to English (no Locale cookie: `localeCookie: false` in `i18n/routing.ts`, so one visit to the other Locale never sticks); it skips `/admin`, `/api`, Next internals and files. Legacy unprefixed Route URLs redirect permanently (308) to English through `redirects()` in `next.config.ts`. A path under a Locale that is no Route (e.g. `/fr/xyz`) is rewritten by `proxy.ts`, with a 404 status, to that Locale's statically generated 404 page `app/[locale]/page-not-found` (in the Locale, inside the normal layout; `app/[locale]/not-found.tsx` shows the same for any `notFound()`). It is a rewrite rather than a catch-all calling `notFound()` because Next 16 renders a dynamic `notFound()` only in the browser, serving an empty `<html id="__next_error__">` shell. URLs outside Locale routing (files, unknown Admin paths) render `app/global-not-found.tsx`. Internal links use `Link`/`usePathname` from `@/i18n/navigation` (Locale-aware), never `next/link` with a bare path.

The one list of Routes is `ROUTES` in `config/routes.ts`: each Route holds its path, the key of its texts under `Routes` in the message dictionaries (`label`, `title`, `description`) and whether it is in the menu. The sidebar menu is generated from it (real links; the active-Route rule is `lib/routes/is-active-route.ts`, applied to the Locale-stripped path). Every page renders `<PageHeader route={ROUTES.x} />` and exports `generateMetadata = routeMetadata(ROUTES.x)` from `components/page-header`, which also declares the page's alternate-Locale URLs. The legacy redirects are derived from `ROUTES` too. Adding a page is one entry in `ROUTES` plus its texts in every dictionary.

**Interface strings** — one message dictionary per Locale in `messages/` (`en.json` is the reference; `global.d.ts` types keys from it, and `messages/messages.test.ts` checks every dictionary has the same keys). Server components use `getTranslations` (from `next-intl/server`), client components `useTranslations`; the Locale comes from the root param (`i18n/request.ts`), so pages need no `setRequestLocale`. Every visible string of a public page (buttons, alt texts, empty states, the contact and MDF 2025 texts, diploma names) is in the dictionaries, so no page mixes languages. Proper nouns (Project titles, Tech names, company and school names) and Video titles stay untranslated.

**Layout** — `app/[locale]/layout.tsx` sets `<html lang>`, wraps everything in `NextIntlClientProvider`, `ThemeProvider` (dark default) and `MobileMenuProvider`, then delegates to `app/[locale]/ClientLayout.tsx`. `ClientLayout` renders the `Sidebar` on the left and a scrollable content panel on the right. The sidebar content is mounted once and only restyled between the desktop column and the mobile overlay, so there is a single Lanyard connection and a single set of menu sounds; mobile open state is managed through `contexts/menu-mobile.context.tsx`.

**Content** — Techs, Tech categories, Projects, Experiences and the Profile live as JSON documents in `content/` (`techs.json`, `tech-categories.json`, `projects.json`, `experiences.json`, `profile.json`); uploaded assets (Project images in `public/images/projects/`, Resume PDFs in `public/pdf/`) stay in `public/`. Edit them by hand or through the Admin. Pages obtain content only through the content catalog in `lib/content/` (Effect v4, server only, see ADR-0002):

- `schema.ts` — Effect Schemas for every document (Localized text with non-empty `en` and `fr`, Tech, Tech category, Project, Experience, Profile; asset paths only name a plain file of their folder: a Project image `/images/projects/<name>.(png|jpg|jpeg|webp|avif)`, a Resume `/pdf/<name>.pdf`, never a sub-folder or `..`, as the Admin commits uploads to `public<path>`) and `Content`, which adds the cross-document rules (a Tech is defined once, every referenced Tech exists). `DOCUMENT_PATHS` maps each kind to its file.
- `period.ts` — the `Period` schema (start `YYYY` or `YYYY-MM`; end the same or `"ongoing"`; end not before start) and the ordering by start, most recent first, ongoing first on equal starts (a year counts as its January). Shared by every kind that has a Period.
- `format-period.ts` — `formatPeriod(period, locale)`, the plain Period formatting function (month names per Locale, "Today" / "Aujourd'hui"); no Effect import, so components may use it. Tested in `format-period.test.ts`.
- `repository.ts` — the `ContentRepository` port (`head`, `read` at a revision, by default the current one, `commit` with optimistic revision); adapters `repository-local-filesystem.ts` (build time, read-only), `repository-github.ts` (the Admin: Git Data API with the Owner's token, one commit per save on `main`, text or binary files, reads at a commit sha through the contents API's `ref`, fast-forward only so a moved `main` is a `ContentConflict`; tested against a fake GitHub `fetch`) and `repository-in-memory.ts` (tests; keeps every revision readable, and `makeInMemoryRepository` also lists the commits made).
- `catalog.ts` — the `ContentCatalog` service: decodes and validates all documents, then returns ready-to-render data (`techCategories` with resolved Techs; `projects` ordered by Period, with resolved Techs, a `repository` only for open-source Projects (the Profile's GitHub link when the Project has none) and, for a Project's own repository, its live GitHub star count, omitted when zero; `experiences` ordered by Period; `profile`; `videos` of the Profile's channel, most recent first, with only the latest marked `isNew` while under 30 days old, read with Effect `Clock`). These members return Localized texts with both Locales (what the Admin edits); public pages use `inLocale(locale)` instead, the same Tech categories, Projects and Experiences with every descriptive text in that Locale (proper nouns and Video titles as they are), plus the Locale's `resume`. Invalid content fails with `ContentInvalid`, naming file and location, which fails the build. Tested in `catalog.test.ts`, `catalog-locale.test.ts` and `catalog-videos.test.ts`; `content.test.ts` checks that `content/` itself is valid.
- `github-stars.ts` — the `GitHubStars` source, consumed only by the catalog: `layer` reads `stargazers_count` from the public GitHub REST API (unauthenticated; any failure is `GitHubStarsUnavailable`), `layerTest` serves fixed counts per repository link.
- `external-source.ts` — what the external sources share: `fetchExternalText` (fetch with `cache: "no-store"`, so responses never land in Next's Data Cache, which `next build` persists in `.next/cache` across deploys), and the `PageGeneration` reference with `orOnColdBuild(fallback)`: on a `"cold-build"` (set by `server.ts` during `next build`, from `NEXT_PHASE`) a failing source falls back (stars omitted, no Videos); otherwise (`"revalidation"`, the default) its failure fails the catalog.
- `youtube-channel.ts` — the `YouTubeChannel` source, consumed only by the catalog: `layer` reads the channel's public Atom feed (no API key; any failure is `VideosUnavailable`), `layerTest` serves fixed Videos per channel. The channel identifier is the Profile's `youtubeChannelId`.
- `server.ts` — what pages call (`getTechCategories(locale)`, `getProjects(locale)`, `getExperiences(locale)`, `getResume(locale)`, `getVideos()`, `getProfile()`; pages pass `await getLocale()`): plain async functions over a `ManagedRuntime`, so React code never imports Effect. `types.ts` re-exports the content types for components (type-only).

Pages format Periods with `formatPeriod(period, locale)` and Video dates with next-intl's formatter, so both follow the Locale. A Tech is rendered only by `components/tech/TechBadge.tsx` (its `#rrggbb` colour, text colour from `lib/text-color-on.ts`).

An Experience's contract type is an identifier (`entrepreneurship`, `permanent`, `work-study`, `internship`); its label is an interface string under `Experiences.contractTypes` in the message dictionaries.

The Profile is Lucas's public identity, defined once: social links (GitHub, LinkedIn, YouTube, Instagram), the YouTube channel identifier (the YouTube link must be that channel's `https://www.youtube.com/channel/<id>` URL), the Discord account identifier and one Resume per Locale (`asset` path under `public/`, `lastUpdated` as `YYYY-MM-DD`). Its consumers read it, nothing is hard-coded: the Locale layout passes it to the sidebar footer (social links) and Presence (Discord account), the home page shows the Locale's Resume and date, the contact page links LinkedIn, the Videos page links the channel. `content.test.ts` checks every Resume asset exists.

Star counts and Videos are never written by hand. The Projects and Videos pages declare `revalidate = 86400` and `dynamic = "force-static"` (needed so the uncached external fetches keep them static): they are regenerated on every deploy and then once a day. When GitHub or the feed fails at runtime, `getProjects()` / `getVideos()` reject, so Next keeps serving the previous page; during `next build` stars are omitted and the Videos page shows its empty state, and the build does not fail. The catalog reads `content/` from `process.cwd()` at runtime too (revalidating pages, and every page's layout reads the Profile), so `outputFileTracingIncludes` in `next.config.ts` ships the folder with every page under `[locale]` (check `.next/server/app/[locale]/*/page.js.nft.json`).

**Presence** — `components/presence/` uses the `react-use-lanyard` library to display real-time Discord presence in the sidebar. `select-presence.ts` is the plain selection rule (tested in `select-presence.test.ts`): it maps the live Lanyard status to playing (a game, which wins), listening (a Spotify track) or nothing, and builds the artwork URLs. The card is derived from the live status on every render, with no stored state. The Discord account it follows is the Profile's `discordUserId`, passed down from the layout.

**Admin** — `app/admin/` is the Owner's private space: French, server-rendered, `noindex`, out of the menu and outside Locale routing (so no `proxy` logic; the access check lives in the Admin itself). `app/admin/layout.tsx` is the Admin's own root layout and its gate: anyone but the signed-in Owner gets the sign-in or refusal screen. Sign-in is GitHub OAuth (scope `public_repo`, the token later used to commit content): `app/admin/auth/sign-in` redirects to GitHub, `app/admin/auth/callback` keeps the identity in an iron-session sealed cookie for 12 hours (no database; the token is kept for the Owner only); any failure there (forged state, declined consent, GitHub refusing the code or unreachable, missing configuration) signs nobody in and redirects back to the sign-in screen, logging no GitHub error text. Signing out (`signOut` in `lib/admin/github-sign-in.ts`) revokes the Owner's token through `DELETE /applications/{client_id}/token` (best effort) and always ends the session. The OAuth App's `public_repo` token can write to every public repository of the Owner; a GitHub App installed on this repository only would narrow that reach (not done). The one Owner check is `ownerAccess` in `lib/admin/owner-access.ts`, behind the `AdminIdentitySource` interface. The Admin layout and home page read it through `currentOwnerAccess()` (`lib/admin/session.ts`); editor pages and every content Server Action reach it through `AdminAccess` (below), which refuses anyone but the Owner with `not-owner`, so each action checks the Owner itself, as Server Actions are public endpoints. Tests use a fake identity source (`owner-access.test.ts`) and a fake GitHub (`github-sign-in.test.ts`).

Content editing follows one pattern, to copy for every editor. `lib/admin/admin-action.ts` holds `AdminAccess` (the signed-in Owner's content repository, or `NotOwner`) and `saveContent(revision, edit)`: read the content through the catalog's `loadContent` at the revision the editor was opened at (never `main`'s possibly lagging current state), apply the edit, validate the whole result with the `Content` schema (issues inside the edited entry, an indexed entry or a whole document like the Profile, become French field errors keyed by input path, e.g. `name.fr`, `techs.1`, `links.github`; any other issue refuses the save), then commit only the changed documents, with any files the edit uploads (`assets`), as one commit on top of the revision the editor was opened at. An upload travels in the editor's form: a Project image (`lib/admin/project-image.ts`, plain code: PNG, JPEG, WebP or AVIF recognised from its bytes, at most 4 MB, stored as `public/images/projects/<title>-<fingerprint>.<ext>` so a new image never reuses a cached URL) is committed with its Project; a Resume (`lib/admin/resume-pdf.ts`, plain code: a PDF recognised from its bytes, at most 4 MB) is committed over its Locale's current file, with the Profile dating that Resume to the upload day in Europe/Paris (read with Effect `Clock`); `experimental.serverActions.bodySizeLimit` in `next.config.ts` (4.5 MB, Vercel's cap; Next cannot scope it to one action) lets it through. Every action returns an `AdminActionResult` (`lib/admin/action-result.ts`, plain data): `saved`, `invalid`, `refused`, `conflict`, `not-owner` or `failed`. Actions per kind live in `lib/admin/<kind>.ts` (e.g. `techs.ts`: Techs, whose identifier is fixed once created, and Tech categories, addressed by position; `experiences.ts`: Experiences, addressed by their position in the stored document; `projects.ts`: Projects, likewise; both editors list them in Period order like the public pages, each with its stored position, through `inPeriodOrder` in `admin-action.ts`, while Techs and Tech categories are listed in stored order, their public order; `profile.ts`: the Profile's links and account identifiers, and Resume uploads), with an `open…Editor` that reads the revision first, then the content; they are tested in `lib/admin/<kind>.test.ts` against an in-memory repository and a fake identity. `lib/admin/server.ts` (server only) runs them over the session and the GitHub repository (`CONTENT_REPOSITORY` in `lib/admin/config.ts`); it is all `app/admin/` imports, so no React code imports Effect. Each editor page (`app/admin/<kind>/page.tsx`) has a `"use server"` `actions.ts` that reads the form and calls `refresh()` after a save; its forms use `AdminForm`, `AdminField` and `LocalizedField` from `app/admin/admin-form.tsx`, and a Period is entered with `PeriodField` (`app/admin/period-field.tsx`: year and optional month for start and end, "en cours" as an end) and read back in the action with `readPeriod` (`app/admin/period-input.ts`, tested in `period-input.test.ts`); the "live in about a minute" notice comes from `AdminNoticeProvider` in the Admin layout.

Admin environment variables (`.env.local` locally, Vercel Production); `scripts/wizards/admin-github-oauth.sh` creates the OAuth apps and sets them all:

| Variable | Value |
| --- | --- |
| `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | GitHub OAuth app credentials; one app per environment, callback `<origin>/admin/auth/callback` |
| `SESSION_SECRET` | ≥ 32 characters, encrypts the session cookie; changing it signs everyone out |
| `OWNER_GITHUB_ID` | The Owner's numeric GitHub id (`gh api user -q .id`); unset means nobody gets in |
| `AUTH_REDIRECT_URI` | Optional, pins the callback URL (set on Production); otherwise derived from the request |

**3D scene** — `app/[locale]/mdf-2025/` contains a Three.js/React Three Fiber scene celebrating a competition win. Uses `@react-three/fiber`, `@react-three/drei`, and `@react-three/postprocessing`.

**UI components** — Shadcn/ui components live in `components/ui/`. Custom typography primitives (`TypographyH2`, `TypographyH3`, `TypographyH4`, `TypographyP`, `Bold`, etc.) are in `components/typography/index.tsx`; prefer these over raw HTML tags for text. They take `children` and an optional `className`; adjust styling through `className` rather than adding props.

**Types** — content types for components come from `lib/content/types.ts`; Lanyard types come from `react-use-lanyard`.

**Images** — remote image hosts are allowed through `images.remotePatterns` in `next.config.ts` (`cdn.discordapp.com`, `media.discordapp.net`, `i.scdn.co`, and `*.ytimg.com/vi/**` for Video thumbnails). Add new hosts there if needed; `images.domains` is deprecated.

## Code conventions

- Path alias `@/` maps to the project root.
- Imports are auto-sorted by `eslint-plugin-simple-import-sort` in groups: CSS → react/next → external packages → `@/` aliases → relative. Run `pnpm lint` to catch violations.
- Prettier enforces double quotes, 2-space indent, trailing commas, semicolons, 80-char line width.
- `"use client"` is only added when a component uses browser APIs, hooks, or event handlers — server components are the default.
